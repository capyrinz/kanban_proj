## 1. Backend Framework: FastAPI (Python 3.10+)

### Почему FastAPI?
1. **Высокая производительность:** FastAPI построен на базе `ASGI`-сервера `Uvicorn` и библиотеки `Starlette`, что обеспечивает скорость работы, сопоставимую с Node.js и Go.
2. **Автоматическая генерация документации:** На основе аннотаций типов Python фреймворк автоматически генерирует интерактивную OpenAPI/Swagger-документацию (`/docs`) и Redoc (`/redoc`), что исключает расхождение между кодом и документацией API.
3. **Строгая валидация данных:** Встроенная интеграция с Pydantic гарантирует проверку типов входящих JSON-запросов «из коробки» и возвращает понятные ошибки (`422 Unprocessable Entity`).
4. **Асинхронность:** Нативная поддержка `async/await` позволяет эффективно обрабатывать параллельные HTTP-запросы.

---

## 2. Валидация и схемы: Pydantic

### Почему Pydantic?
1. **Безопасность типов:** Автоматически приводит и проверяет типы данных для моделей колонок, задач и проектов.
2. **Сериализация данных:** Простая конвертация внутренних Python-объектов и словарей в JSON для ответов API.
3. **Читаемость кода:** Схемы (`ColumnCreate`, `TaskResponse` и др.) служат единым источником правды для структуры данных в проекте.

---

## 3. Frontend: Vanilla HTML5 / CSS3 / JavaScript (ES6+)

### Почему без фронтенд-фреймворков (React/Vue/Angular)?
1. **Минимализм и легковестность:** Для академического/учебного проекта использование чистого JavaScript (ES6) с `Fetch API` исключает избыточную сложность сборщиков (Webpack/Vite) и тяжелые `node_modules`.
2. **Простота развертывания:** Фронтенд нативно раздается FastAPI как статические файлы (`StaticFiles`), что позволяет запускать приложение «в одно нажатие» без отдельного сервера для фронтенда.

---

## 4. Среда выполнения и ASGI-сервер: Uvicorn

### Почему Uvicorn?
1. **Стандарт для FastAPI:** Uvicorn является молниеносным ASGI-сервером, поддерживающим протоколы HTTP/1.1 и WebSockets.
2. **Режим разработки:** Флаг `--reload` обеспечивает отслеживание изменений в файлах `.py` и горячую перезагрузку сервера без ручного перезапуска.

## 5. Тестирование и качество кода (QA Stack)

### 5.1. Фреймворк тестирования: Pytest
* **Причина выбора:** Удобный синтаксис, мощный механизм фикстур (`fixtures`), детальный вывод ошибок и возможность интеграции со всеми плагинами покрытия.

### 5.2. Интеграционный клиент: FastAPI TestClient (httpx)
* **Причина выбора:** Позволяет выполнять HTTP-запросы (`GET`, `POST`, `PUT`, `DELETE`) к эндпоинтам без физического подъема сетевого порта, что делает интеграционные и E2E-тесты мгновенными.

### 5.3. Анализ покрытия кода: Coverage.py
* **Причина выбора:** Отображает точный процент покрытия строк кода автотестами и указывает на незатронутые ветки бизнес-логики (`coverage report`).

### 5.4. Статический анализ и линтинг: Flake8 & Bandit
* **Flake8:** Гарантирует соблюдение стандарта оформления кода PEP8.
* **Bandit:** Сканирует Python-код на предмет багов безопасности (например, жестко заданные пароли, небезопасные импорты).
* **pip-audit:** Проверяет зависимости проекта на известные уязвимости (CVE).

### 5.5. E2E-тестирование: Playwright (pytest-playwright)
* **Причина выбора:** реальные тесты в браузере (Chromium) на том же pytest: проверяют UI-сценарии (логин/регистрация, CRUD карточек, drag-and-drop, фильтры, экранирование XSS) на живом сервере, а не мокают фронтенд.

### 5.6. Нагрузочное тестирование: Locust
* **Причина выбора:** Python-сценарий виртуальных пользователей (`locustfile.py`) легко читается и расширяется, замеряет RPS/время отклика/перцентили и поддерживает прорампливание пользователей для проверки NFR.

## 7. Хранение данных: SQLAlchemy 2.0 (async) + SQLite + Alembic

### Почему такой набор?
1. **Соответствие требованиям лабораторной:** задание требует ORM и миграции — SQLAlchemy (async-движок + `aiosqlite`) и Alembic закрывают это без смены заявленного стека.
2. **Безопасность против SQLi:** все запросы строятся ORM с параметризацией — пользовательский ввод не подставляется в SQL-текст.
3. **Alembic вместо `create_all`:** схема управляется версионированными миграциями (`alembic/versions`), изменение модели воспроизводимо и проверяемо в CI; `init_db()` при старте приложения применяет `alembic upgrade head`.
4. **Переносимость:** SQLite позволяет запускать приложение и все тесты без внешней СУБД; смена `DATABASE_URL` на PostgreSQL не требует изменения кода.

## 8. Аутентификация и безопасность: PyJWT + bcrypt

* **PyJWT:** выпуск и проверка HS256-токенов (`sub`, `role`, `exp`) без устаревших библиотек вроде `python-jose`.
* **bcrypt:** хеширование паролей (параметризуемое число раундов, в тестах — 4 для скорости).
* **Модель угроз:**
  * *SQLi* — закрыт параметризацией SQLAlchemy;
  * *XSS* — весь пользовательский вывод экранируется на фронтенде (`esc()`), проверяется E2E-тестом;
  * *CSRF* — API использует заголовок `Authorization: Bearer` (не cookie), поэтому браузерные CSRF-векторы неприменимы;
  * *brute force/роли* — отдельные эндпоинты ролей (`require_roles`) и запрет саморегистрации `administrator`.

## 9. CI/CD: GitHub Actions

* **Строгий конвейер** без `|| true`: flake8 → unit → build → integration (+ gate покрытия 80/70) → Playwright E2E → bandit + pip-audit → deploy.
* Каждый шаг падает при ненулевом коде возврата, поэтому регрессия не попадает в `main`.
* Трейсы Playwright при падении E2E выгружаются как артефакт для отладки.
