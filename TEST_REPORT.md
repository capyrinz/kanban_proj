## 5. Нагрузочное тестирование (Locust)

Сценарий `locustfile.py`: авторизация, чтение доски/поиск, полный CRUD-цикл задачи
(создание → обновление → перемещение → комментарий → удаление) в выделенной колонке
с WIP=1000, чтобы бизнес-ограничения не искажали замер. Прогон: `--headless`, ramp 10–25 юзеров/с.

| Метрика | 50 пользователей, 45 с | 200 пользователей, 60 с |
|---|---|---|
| Запросов / ошибок | **6713 / 0 (0%)** | **8405 / 0 (0%)** |
| RPS | 148.6 | 139.7 |
| Среднее время отклика | **75 мс** | 1119 мс |
| Медиана (p50) | **35 мс** | 930 мс |
| p90 / p95 / p99 | 150 / **230** / 720 мс | 1900 / 2700 / 4100 мс |
| Максимум | 3108 мс | 6798 мс |

**Выводы:**
* При 50 пользователях API отвечает в среднем за 75 мс (< 200 мс по ТЗ), ошибок нет;
  чтение (`GET /tasks`) — p95 48–120 мс, запись медленнее из-за сериализации записей SQLite.
* Насыщение платформы наступает ~140–150 RPS: при 200 пользователях очередь запросов
  растёт (p50 930 мс), т.е. упираемся в однопоточность записи SQLite на dev-машине WSL,
  а не в код приложения (0 ошибок, RPS не падает). Требование «< 200 мс @ 1000 юзеров»
  выполнимо только на выделенном сервере с многопоточной СУБД (см. рекомендации, §9).

## 10. Заключение и рекомендации

**Пройдено:** все функциональные требования п. 3.1 покрыты 94 автотестами (unit — 34,
интеграционные — 47, E2E — 13), покрытие 100% строк / 100% ветвей при требовании 80/70;
нефункциональные требования по bcrypt, XSS/CSRF/SQLi, статическому анализу и работе
с 10 000 карточек выполнены; CI строгий и воспроизводимый.

**Ограничения и рекомендации:**
1. **Производительность на 1000 юзеров:** на dev-машине (WSL + SQLite) насыщение ~150 RPS;
   для NFR «< 200 мс @ 1000 юзеров» требуется PostgreSQL (или выделенный сервер) —
   код асинхронный и готов к смене `DATABASE_URL`.
2. **Пагинация `GET /tasks`:** выгрузка всех 10 000 карточек ~180 мс и 2.7 МБ трафика;
   `limit/offset` сократит отклик и трафик в разы.
3. **ZAP/DAST** запускается вручную (не в CI — требует контейнер и настройку исключений),
   результаты фиксируются в настоящем отчёте; bandit + pip-audit покрывают статическую часть в CI.
4. После инициализации git-репозитория и пуша убедиться, что все 7 джобов зелёные на GitHub.

**Воспроизведение всех проверок:**
